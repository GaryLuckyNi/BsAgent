# 规划前工具能力召回与候选复用设计

日期：2026-10-25

状态：用户已确认方案边界；本设计细则待审阅，尚未实施。

## 一、目标与范围

保留 Router 与 Planner 的独立职责，不新增模型节点。只有 Router 决定需要外部工作、进入 `plan` 时，才在 Planner 内部、调用规划模型之前执行一次本地工具能力召回。

本次解决的是“Planner 不知道某个普通工具已覆盖完整目标，先拆任务导致执行偏移或重复”，不是消除 Planner 本身的调用。普通工具的能力摘要提前披露，完整工具 schema、参数生成和执行仍由执行层负责。

不向模型注入全量工具，不建立逐接口维护的字段映射，不改写 Admin Skill 配置，不改动审批、权限恢复、回执核实和合成层重新规划边界。简单查询绕过 Planner 留待后续单独评估。

## 二、已核对的现状与失败样例

- `backend/app/graph/nodes/planner_agent.py` 的 `_discover_capabilities` 当前忽略 `tool_search_service`，仅发现 Skill。
- `PlannerCapabilities` 和规划输入只有 Skill，没有普通工具的能力摘要。
- 普通工具在 Tool Agent 中，基于拆分后的 `tool_search_query` 或 `task_goal` 才召回。
- 单个普通 Tool Agent 任务当前只支持一次工具选择与调用；确实需要前一步结果作为下一次调用参数时仍须表达依赖，不通过缩减任务掩盖多轮执行。

用户样例：

> 获取银之杰基础信息数据，包括股票代码、名称、上市日期、退市日期等。

项目既有真实观测中，`mcp.tushare.stock_basic` 的描述明确覆盖这些信息，输入支持 `name`；返回字段提示包含 `ts_code`、`name`、`list_date`，并可显式指定 `delist_date`、`list_status`。这只是验证样例，不是写入程序的接口特例，也不保证当前数据源一定成功返回数据。

预期是一个基础信息取数任务。不得无依据扩展成公司画像，或拆成公司识别、上市信息、退市信息等重复查询。参数生成层应依据当次实际 schema 请求必要字段；未返回退市日期不能脱离上市状态自动解释为“未退市”。

## 三、方案取舍

| 方案 | 优点 | 代价或限制 | 决定 |
| --- | --- | --- | --- |
| 规划前召回少量工具能力，仍由 Planner 判断最少任务 | 复用现有检索与执行链路，无额外模型调用，解决规划信息不对称 | 仍有一次 Planner 调用；召回存在漏检 | 本次采用 |
| 召回后先交给 Tool Agent，复杂时升级到 Planner | 简单查询可能省掉 Planner | 新增升级条件、部分覆盖判断与重复执行边界 | 本次不做 |
| 只修改规划提示词 | 改动小 | 看不到工具能力，无法可靠判断单工具覆盖 | 不作为完整方案 |

“Skill 优先”改为条件性的业务匹配原则：当用户目标确实需要 Skill 声明的流程和约束时优先复用；不能仅因 Skill 包含某个取数字段就运行整套流程。对超出目标的固定 Skill 不裁剪或绕过其步骤，而应选择更合适的普通工具任务。

## 四、职责与数据流

### 4.1 Router

保持现有 `direct_answer`、`synthesize`、`plan` 分流和 `available_information` 契约。直接回答及直接合成分支不触发新增检索。Router 不增加工具选择职责，不增加一次意图判断调用。

### 4.2 本地能力发现

在现有 Planner 能力发现入口中复用 `ToolSearchService` 和当前运行的工具目录快照，无需新建 Agent 或图节点。

- 首次以原始用户 query 为主召回，不先拆任务，也不调用模型改写搜索词。指代性或长文本请求，可将 Router 已有的明确目标作为辅助检索文本，不复制整份 `available_information`。
- 普通短 query 单次检索；原文不完整或长度超限时才使用辅助检索，合并去重后仍遵守同一个候选上限，不追加模型调用。检索输入遵守现有 512 字符上限，发生截断必须记录，不能把截断后的未命中宣称为“无能力”。
- 候选上限复用 `tool_search_top_k`，默认 5，最多 8；复用现有 exact/BM25 排序与资格规则，不另造语义评分系统。
- 继承租户、用户、声明权限、市场和时间兼容性约束；声明权限过滤不等于提前知道 TuShare 账号对每个接口的实际权限。
- `search_tool` 不作为业务候选。`web_search` 仍按现有执行策略参与选择，不用其通用描述挤掉专业接口召回名额。
- 候选只表示可考虑的能力，不是覆盖完整目标的证明，更不是调用授权。

### 4.3 Planner

一次规划模型调用，同时接收原有 Skill 摘要、已有信息和少量工具能力卡片。按以下顺序判断：

1. 当前上下文已满足哪些目标，不重复取证。
2. 某个普通工具是否能一次覆盖尚缺的信息，包括查询条件、目标字段和来源约束。
3. 是否确有需要完整执行的业务 Skill，而不是因为主题接近就选用。
4. 只有候选能力不能表达为单次执行，或存在真实数据依赖、不同来源核验、不同独立目标时才拆分。

Planner 负责能力覆盖和任务边界判断，不生成工具参数，不将检索分数当作确定性置信度。可以给任务附上已披露候选引用；最终工具选择、参数校验和执行仍由 Tool Agent 完成。

同一接口并非全计划只能调用一次：不同必要查询参数或前后依赖确实要求多次调用时允许多任务。禁止的是覆盖相同目标且无新增价值的重复工作，不用“工具名相同”作为去重规则。

### 4.4 执行层

普通任务有候选引用时，优先直接解析对应快照工具，不再仅因 Planner 改写了任务文字就重复 BM25 搜索或换掉候选。

复用前验证目录摘要、工具身份与版本，并重新应用当前权限、运行时已知不可用状态和任务市场/时间兼容性约束。当前任务明确不兼容的候选不得执行。

没有引用的任务，包括根问题召回未覆盖的子问题，保持现有按任务检索路径。引用候选经校验均不可用时，区分原因：

- 原任务候选不适用或召回遗漏：允许一次现有任务级检索，不进行隐藏的模型重路由。
- 已知权限拒绝或来源切换要求确认：进入现有恢复流程，不通过重检索、换名或换工具绕过确认。
- 目录发生变化：沿用现有目录一致性保护，不能把旧引用静默绑定到新执行器。

固定 Skill 步骤继续按其明确工具名与冻结版本执行，不合并普通任务候选，也不以普通工具回退替代固定步骤。

## 五、最小数据契约

以下是待实施的内部契约，不是现有字段。

### 5.1 运行级候选快照

在 State 中增加可选 `planning_tool_candidates`，保存：

- `catalog_digest`：本轮工具目录身份。
- `query_fingerprint`：实际检索文本的指纹，避免同轮重复召回。
- `truncated`：检索文本或卡片是否截断。
- `candidates`：有界候选数组。

每个候选包含稳定 `ref`、完整工具名、版本、原始用途描述，以及从现有 schema 确定性投影出的必要参数与关键字段描述片段。若 `fields` 等参数描述声明了可返回字段，应保留相关提示；有输出 schema 时也可抽取其顶层字段。只使用工具自身元数据，不由模型补造返回字段，不维护 `stock_basic` 专属字段表。

单卡片描述与 schema 片段合计最多 1,200 字符，全部卡片合计最多 8,000 字符。超过预算显式标记截断；不能把字段未显示推断为工具不支持。确切 schema 在执行前读取。保持既有 Skill 披露方式，不在本次扩展全量 Skill 检索优化。

卡片不含工具参数值、凭证、执行结果、完整 schema 或工具对象。完整 schema 不进入规划模型上下文，但本地投影允许读取当前目录已有 schema。

### 5.2 任务引用

普通任务增加可选 `tool_candidate_refs`，默认空列表，最多 8 项，仅允许引用当前候选快照中已披露的工具。Skill 任务和纯分析任务不得携带普通工具引用。

引用是候选集合，不是强制执行指令。一个任务引用多个互相替代的候选，不表示必须逐个调用。引用不允许越过既有业务授权、来源约束与审批。

执行器按引用读取运行级卡片及目录，不在每个任务中重复保存工具描述和 schema。未知引用或非法组合视为计划契约错误，复用现有有界格式修复，不接受模型臆造工具名。

## 六、兼容、错误与恢复

- 旧 checkpoint 没有新快照或任务引用时，按旧路径执行，不要求用户迁移历史记录。
- 同一请求相同检索输入和目录摘要复用候选；合法重新规划时按当前目标和目录校验，不无条件复用旧计划的引用，也不丢失历史执行限制。
- 检索无命中或服务未注入时，给 Planner 空工具候选及简短原因，保留 Skill 和按任务检索的既有能力；不因此强制选择 Skill、强制 web search 或触发 replan。
- 只有预期的检索可用性错误可按空候选降级；目录身份冲突、非法状态和程序错误不能被宽泛异常捕获掩盖。
- 候选描述、参数说明和 Skill 正文均是不可信材料，只作能力元数据，不可更改系统策略。
- 现有权限确认 interrupt、批次恢复、工具审批和 unknown 回执核实保护保持不变。没有真实远端调用的预检失败不能伪造执行回执。
- 不通过本次优化修正 Admin 历史 Skill 内容；无效定义仍是独立配置问题。

## 七、观测与成本边界

在现有 Planner 和 Tool Agent 观测中增加有界摘要，不新增模型评审：

- 规划前召回的耗时、候选数、工具身份、目录摘要、命中方式、截断和空候选原因。
- Planner 输出的任务数、Skill 选择及候选引用。
- 执行候选来自 `planning_reuse`、`task_search` 或 `skill_named_tool`，未复用时记录可解释原因。
- 保留模型调用数、Token、工具调用及恢复路径，以便对比实际效果。

不复制全量目录、完整参数或工具结果到新的观测字段。规划前检索是本地处理，不消耗 web search 或真实工具执行预算。候选更多不保证总 Token 更少；本次预期收益是减少错误拆分导致的额外执行和模型调用，须实测确认。

## 八、验收条件

### 确定性与图级测试

1. 使用通用元数据构造工具目录，原始样例召回 `stock_basic`；无专属接口分支。
2. Planner 输入同时有 Skill 和有界工具卡片，没有全量 schema；`available_information` 仍能复用。
3. 脚本化模型输出一个基础信息任务，执行层复用其候选；无重复检索、无公司画像 Skill、无额外上市/退市子任务。
4. 单个工具支持名称查询时，不先凭空创建实体解析任务；若另一工具确实只接受未知代码，则可以保留必要前置任务。
5. 管理层薪酬持股等真正匹配固定流程的请求仍能选择 Skill，并按原步骤、校验及中断恢复完成。
6. 混合问题或多步依赖可以拆分；缺少对应根候选的子任务仍可按任务检索，不能被根候选锁死。
7. 候选引用非法、版本不符、目录变化、权限拒绝、全部不兼容、空命中和截断均有明确测试。
8. 旧 checkpoint 以及 Router 的直接回答、直接合成分支行为不变；权限恢复不被候选复用绕过。

### 真实模型与 Trace 验证

以用户原始 query、同义改写、明确需要多步的请求及真实 Skill 请求构成小批样例。区分脚本化图测试与真实模型能力，不能用预设正确计划证明真实 Planner 一定拆对。

对核心 query 检查候选召回、实际计划、工具参数和完整 Trace：应形成一个 `stock_basic` 取数任务，不产生额外画像维度和重复任务。若真实接口返回权限或网络错误，准确记录为外部执行限制，不能把未取到数据称为成功；但仍可核验规划与候选复用是否正确。

本阶段不以“零 Planner 调用”为验收指标，不保证一定降低每个请求的延迟，不把一次成功当作全场景召回保证。

## 九、自检

- 已明确能力提前披露与完整 schema 延迟加载的区别。
- 已明确 Skill 不再因局部主题相似而无条件优先，但保留固定工作流完整性。
- 已明确候选引用不授权、执行时仍重检安全约束，失败不隐式换来源。
- 已保留未命中子问题和旧 checkpoint 的路径，无需全量工具上下文或新 Agent。
- 本文件是设计，不表示运行代码、Admin 配置或线上行为已经改变。
