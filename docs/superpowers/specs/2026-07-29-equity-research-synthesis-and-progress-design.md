# 投研综合分析与产品进度反馈设计

## 背景

当前 A 股投研链路已经能够完成意图识别、任务规划、MCP 市场数据调用、RAG 检索和最终回答生成，但实际回答仍表现为字段查询结果，而不是投研分析。

根因不是单一工具缺失。运行轨迹显示，`analysis_agent` 只负责整理结构化工具事实，没有生成分析结论；`synthesizer` 又被限制为只能改写 claims。当 LLM 输出触发事实或数字守卫时，系统会静默退回确定性字段模板，导致用户只能看到机械式数据罗列。

流式接口目前也存在产品反馈空窗。工具、RAG 和最终 LLM 调用期间虽然内部 trace 持续产生，但产品端没有稳定的业务进度事件。最终回答是在图执行完成后按固定字符切片发送，不代表 LLM token 的真实生成过程。

## 目标

- 让最终 LLM 在证据约束下完成真正的投研综合，而不是逐字段改写。
- 保持金融事实边界，禁止模型新增无来源数字、事件和确定性预测。
- 当模型输出校验失败时暴露可观测原因，并进行一次受约束修复，不再静默降级为机械长列表。
- 在耗时阶段向用户持续展示业务语义明确的进度提示，不暴露内部节点、trace、系统提示或工具参数。
- 支持 Enter 发送、Shift+Enter 换行，并兼容中文输入法组合输入。

## 非目标

- 本轮不新增历史行情、同行比较、技术指标或公告数据工具。
- 本轮不在产品端展示 node trace；trace 继续只用于调试和观测。
- 本轮不增加第二次独立的 LLM 分析调用，避免进一步增加成本和响应时间。
- 本轮不向用户展示模型隐藏推理或逐 token 的内部思维链。

## 后端设计

### 证据标准化

`analysis_agent` 继续承担确定性证据标准化职责：

- 汇总成功的 MCP 工具结果、RAG evidence 和数据覆盖情况。
- 生成统一的事实集合，每条事实包含稳定引用、业务标签、原始值和来源。
- 标记缺失字段、失败能力和数据时间边界。
- 不在代码中枚举具体公司的投资结论。

这一层保持确定性，使工具适配和事实校验可以独立测试。

### 投研综合

`synthesizer` 从“答案渲染器”升级为“证据约束下的投研分析师”。输入包括：

- 用户原始问题和 Planner 识别出的分析维度。
- 标准化市场事实及其引用。
- RAG 证据及引用。
- 数据覆盖、失败能力和缺失信息。

宽泛的公司分析默认组织为：

1. 核心判断。
2. 业务与行业。
3. 财务质量。
4. 行情与估值。
5. 主要风险。
6. 数据边界。

模型可以从证据形成定性判断，例如亏损、经营现金流承压或估值指标较高，但不得新增事实、数字、公告或预测。没有足够证据的维度必须明确说明，而不是补全常识性内容。

### 输出守卫与修复

最终回答继续经过数字和证据守卫：

- 回答中的事实数字必须能在事实集合或 RAG 证据中找到。
- 重要分析结论必须至少关联一条事实或证据。
- 不允许确定性涨跌预测、收益承诺或无证据事件。
- 金融免责声明由系统确定性追加。

首次 LLM 输出校验失败时，系统使用校验原因和原始证据执行一次低温度受约束修复。第二次仍失败时返回简洁、可读的安全降级回答，并在 `response_policy` 和 trace 中记录具体降级原因。安全降级不再展开原始字段长列表。

### 产品进度事件

流式接口新增 `progress` SSE 事件，payload 采用稳定产品契约：

```json
{
  "stage": "collecting_market_data",
  "message": "正在获取公司、行情与财务数据"
}
```

首版阶段包括：

- `planning`：正在规划分析范围。
- `collecting_market_data`：正在获取公司、行情与财务数据。
- `retrieving_knowledge`：正在检索补充资料。
- `analyzing_evidence`：正在核对并分析已获得的证据。
- `composing_answer`：正在生成最终投研报告。

进度事件由后端根据图状态转换产生，与内部 trace 分离，不携带节点名、调用参数、错误堆栈或隐藏推理。相同阶段只发送一次。收到首个 `answer_delta` 前，前端持续展示当前进度；答案开始后立即隐藏。

## 前端设计

### 输入行为

- 表单保留原生 submit 语义。
- textarea 按 Enter 时阻止默认换行并提交。
- Shift+Enter 保留换行。
- `KeyboardEvent.isComposing` 或 `keyCode === 229` 时不提交，避免中文输入法确认候选词触发发送。
- busy 状态下忽略重复提交。

### 进度展示

Agent 消息区域增加一条紧凑的运行状态提示，使用当前 `progress.message`。该提示不是思考过程，也不显示 trace。

- 思考摘要完成后可以收起，但进度提示继续存在。
- 收到新的 progress 时原位更新文案，不追加历史列表。
- 收到 `answering` 或首个 `answer_delta` 时立即移除进度提示，并同步收起思考面板。
- 请求失败时移除进度提示并展示现有错误反馈。

## 数据流

用户提交问题后，Intent Router 和 Planner 明确分析范围。Planner 完成后，流式接口发送市场数据采集进度；MCP 结果返回后按计划决定是否显示知识检索进度；证据收集结束后显示分析进度；进入 Synthesizer 前显示报告生成进度。Synthesizer 基于标准化事实生成分析回答并通过守卫，随后开始发送答案内容。

## 错误处理与可观测性

- MCP 或 RAG 的可选能力失败通过数据边界写入回答，不中断已有证据可支持的分析。
- LLM 首次校验失败和修复结果记录在 `response_policy.llm_rendering`，trace 只保存安全摘要。
- 产品 progress 不复用 trace 文案，避免内部实现泄漏和前端对节点名称产生耦合。
- LLM、工具和 RAG 的实际耗时继续由 trace 记录，产品端只展示业务状态。

## 测试策略

- 后端单元测试验证：宽泛公司分析提示要求形成观点而非字段罗列；不支持数字会被拒绝；一次修复成功后采用修复结果；二次失败进入简洁安全降级。
- 后端接口测试验证：progress 事件按业务阶段发送、去重，并且 payload 不包含节点名和工具参数。
- 前端单元测试验证：Enter 提交、Shift+Enter 换行、输入法组合态不提交；progress 解析与状态替换；首个答案片段立即清除进度。
- 前端构建验证 TypeScript 和 Vite 输出。
- 本地真实链路验证“分析一下岩山科技”，检查报告结构、分析观点、数据边界和进度时序。

## 验收标准

- 最终回答包含基于证据的判断和风险解释，不再只是逐字段输出。
- 回答不新增证据之外的数字或公司事件。
- 工具、检索、分析和报告生成期间前端都有明确提示，不出现无反馈空窗。
- Enter 可以发送，Shift+Enter 可以换行，中文输入法不会误发送。
- 产品端不展示 node trace 或内部工具参数。
