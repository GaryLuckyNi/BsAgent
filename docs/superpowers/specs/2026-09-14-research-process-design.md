# AI 研究过程展示设计

## 背景

DeepSeek 思考模式会分别返回 `reasoning_content` 和 `content`。当前实现把 `reasoning_content` 逐 token 转发到产品界面，导致界面展示英文自言自语、提示词复述、反复修正和内部控制信息。它虽然来自真实模型响应，但不是适合用户阅读的产品内容。

## 目标

界面需要真实呈现研究发生了什么，同时保持内容简洁、稳定、可恢复：

1. 原始 `reasoning_content` 只存在于 LLM 客户端返回值和调试测试中，不进入公开事件、会话元数据和前端。
2. “研究过程”来自实际计划、工具调用和分析结果，不伪装成模型逐步思维链。
3. 最终 `content` 独立流式输出，不与研究过程混排。
4. 刷新会话后仍能恢复已经展示的研究过程。

## 事件模型

公开 `progress` 事件增加 `kind`：

- `status`：当前阶段状态，只更新顶部状态，不写入过程时间线。
- `activity`：真实工具或技能活动，使用同一个事件 ID 更新开始、成功或失败状态。
- `summary`：计划摘要或分析结论，作为可阅读的过程内容进入时间线。

所有公开文本在后端边界做长度限制和内部标识过滤。若节点没有合适的公开摘要，则退化为简短状态，不暴露原始输出或提示词。

## 节点行为

- `intent`：只报告正在理解问题。
- `planner`：开始时报告状态；完成时从结构化计划的 `public_summary` 生成计划摘要。
- `tool_agent`：基于真实任务和执行结果更新活动状态。
- `skill_agent`：开始时记录活动；完成时可从安全的节点结果提取简短摘要。
- `analysis`：开始时报告状态；完成时从分析结果提取关键发现摘要。
- `synthesizer`：只流式输出最终答案，不重复研究过程。

## 原始思考数据边界

`DeepSeekClient` 在流式调用中累积 `reasoning_content`，并放入 `LlmCompletionResult.reasoning_content`。这个字段仅供后端调用方诊断和自动化测试使用。公开事件生成器忽略 reasoning delta，服务端不会把原始思考写入 SSE、AG-UI 事件或会话存储。

## 持久化与恢复

服务端在流式执行期间收集 `activity` 和 `summary` 事件，按 ID 合并状态并限制数量与文本长度，最终写入 assistant message 的 `metadata.research_process`。前端从会话消息恢复该字段，并沿用事件的稳定顺序渲染。

## 前端交互

折叠区标题改为“正在研究…”或“研究完成（用时 N 秒）”。时间线中：

- `summary` 使用 Markdown 文本显示计划或发现。
- `activity` 使用图标、状态和简短说明显示真实执行。
- 旧会话里的 legacy reasoning 数据仍可兼容读取，但新请求不再产生该数据。

## 验收标准

1. DeepSeek 流式响应中的 reasoning 与 answer 同包或分包时均可正确解析。
2. 浏览器网络事件中不出现原始 `reasoning_content` 文本。
3. 计划、工具执行和分析摘要按发生顺序显示，活动开始与结束不重复。
4. 失败活动明确显示失败，后续阶段不会残留为“进行中”。
5. 刷新页面后研究过程可以恢复。
6. 最终答案仍逐步流式显示，且不会混入研究过程。
