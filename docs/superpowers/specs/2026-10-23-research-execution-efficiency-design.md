# 投研执行效率修复设计

## 授权与依据

用户已认可最新真实 Trace `e30146f25b95e96c4651e26a850c8501` 的链路分析并要求开始修复。该请求主流程有 8 次可见 Generation；估值任务搜索偏题、第一次修订仅改变摘要、终端分析与合成重复。Router 的 61 秒等待原因未确定，本轮不猜测性切换模型、接口或超时。

后续用户明确该等待视为偶发，本轮不再调查该个例。

## 实施边界

1. 无执行差异的 revise 转为 continue（仍有就绪任务）或 finish（无可推进任务），保留缺口，不新增纠错调用，不消耗修订次数。
2. Planner 通过可选 `synthesis_task_id` 显式将唯一就绪的终端 analysis 任务交给最终回答节点；只允许 finish，必须无后续消费者、无其他未完成任务且依赖成功。最终节点承接推理预算并记录完成，不按拓扑猜测删任务，不跳过取证后的评审。
3. 各模型使用确定性的输入投影：当前问题不重复传；JSON 内容转对象；搜索来源集中去重；合成不接收 query、调度 action、重复缺口或空字段。原始 State、artifact、回执和权限快照保留。
4. 通过已有本地工具 `run_with_context` 通道向搜索服务绑定可信 task_goal、completion_criteria、as_of；这些信息由服务端传递，不由模型伪造，也不改变已审批参数。搜索返回独立的证据覆盖状态，不把请求成功当作目标完成，不依据覆盖自述跳过 Planner。
5. 每次搜索服务模型请求记录独立 Generation、用量与续轮，汇总各轮 usage；Judge 不擅自改变默认采样策略，先补充可用于核实的证据上下文。

不维护 MCP 只读接口白名单，不合并或绕过权限 interrupt，不引入额外压缩/校验模型，不自动重放工具。

## 验收

- 原始三任务无效修订回放不增加 iteration、不改名、不重试。
- 显式终端分析交接由 8 次主流程可见调用降为 6 次的离线链路回放；中间分析、有待执行工具、失败依赖、非法 ID 均不可交接。
- 输入投影测试验证对象化、缺口和来源去重、审计原文不变。
- 可信估值目标与时点进入搜索请求，即使建议 query 是“暴跌原因”；覆盖未知/缺失可见，续轮保留上下文，每轮观测和 token 可核对。
- 权限回退集成、全量后端、静态检查保持通过；真实请求比较只报告实测，不预承诺延迟比例。
