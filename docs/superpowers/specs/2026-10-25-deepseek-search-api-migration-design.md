# DeepSeek Search API 直连迁移设计

日期：2026-10-25

状态：用户已确认第一阶段方案并授权自主设计、实施与验证。第一阶段已实现，验证证据与限制见 `docs/acceptance/2026-10-25-deepseek-search-api-migration.md`；Fetch 保留为第二阶段。

## 一、目标与范围

将现有 `web_search` 从 DeepSeek Anthropic Messages 服务端搜索迁移到独立 Search API，去掉搜索内部的辅助模型调用，直接将来源摘要交给现有研究链路使用。

本阶段完成：

1. Search API 客户端、工厂、配置与工具注册。
2. 保持来源、摘要、日期在普通执行、权限恢复和模型输入投影中的可用性。
3. 正确表达空答复、未知覆盖状态、错误、执行身份和 API 观测。
4. 完成确定性测试及具备环境条件时的真实接口验证。

Fetch 作为第二阶段的独立 `web_fetch` 工具接入。本阶段不自动抓取搜索结果，不新增工具循环、模型节点或覆盖判断模型，不扩展现有权限恢复授权范围。

## 二、已核对的现状与方案取舍

### 2.1 现有链路

`Tool Agent → WebSearchTool → DeepSeekWebSearchClient → /anthropic/v1/messages → 服务端搜索与答复生成`。

- `backend/app/search/deepseek.py` 同时承担 HTTP 请求、搜索续轮、来源提取、答复生成结果解析和模型覆盖自述解析。
- `backend/app/search/factory.py` 只支持 `deepseek` 模式，搜索使用模型地址和模型名称。
- `backend/app/tools/web_search.py` 的输入允许 500 字符，最大结果数为 10，公共异常直接依赖旧客户端模块。
- `backend/app/tools/default_registry.py` 将搜索注册为本地平台工具；Gateway 仅对本地和 RAG 执行绑定调用 `run_with_context`。
- 搜索预算和回执复用绑定工具调用身份及执行绑定摘要，不能只替换客户端而不区分新旧实现。
- `backend/app/graph/recovery/executor.py` 的恢复内容保留总答复和标题链接，未保留来源摘要；新接口无总答复时会丢失模型判断所需的证据内容。
- 当前普通工具子任务执行一次调用后返回结果，没有搜索后在同一任务内任意追加 Fetch 的循环。

### 2.2 方案选择

| 方案 | 收益 | 代价 | 决定 |
| --- | --- | --- | --- |
| Search 直连，返回来源摘要 | 去掉内部模型生成，改动集中，复用现有调度 | 不再提供搜索模型生成的总答复和覆盖自述 | 第一阶段采用 |
| Search 后自动 Fetch 每个来源 | 每次都尝试获得正文 | 请求量、延迟和上下文增加，抓取未必必要 | 不采用 |
| Search 与 Fetch 分别作为工具 | 可针对证据缺口选择阅读原文 | 需要独立权限、预算、回执和候选披露设计 | 第二阶段 |

## 三、上游协议与客户端边界

官方依据：

- [网页搜索与抓取指南](https://api-docs.deepseek.com/zh-cn/guides/search/)
- [Search API Reference](https://api-docs.deepseek.com/api/search/)
- [Fetch API Reference](https://api-docs.deepseek.com/api/fetch/)

新增 `DeepSeekSearchApiClient`，使用现有 `httpx` 依赖，不新增 SDK。请求固定为 `POST /v1/tools/search`，以 Bearer 请求头注入现有 DeepSeek API Key，不把凭证放入查询词、URL 或工具参数。

客户端只负责请求、协议验证、来源归一化和稳定错误转换；不生成查询词、不判断金融实体、不推断研究目标完成。

### 3.1 输入

| 字段 | 本阶段约定 |
| --- | --- |
| `query` | 去除首尾空白后为 1～128 个 Unicode 字符；工具输入与客户端校验一致，超长明确拒绝，不静默裁剪或调用模型重写 |
| `count` | 由 `max_results` 映射；保留默认 5、范围 1～10，不因上游允许 50 就扩大项目上下文 |
| `need_content` | 固定为 `false`，不向模型开放该参数 |
| `ori_question` | 只有可信服务端上下文提供真实原始问题、去除首尾空白后不超过 128 字符，且既有凭证检测和脱敏策略均未发现敏感内容时传入，否则整体省略；不使用子任务目标或脱敏片段冒充原始问题 |
| `localization` | 省略，不收集用户 IP |

`SearchResearchContext` 可增加向后兼容的可选 `original_question`，仅由现有 Gateway 上下文构建位置绑定合法短原文，默认不提供。长原文不截断后冒充完整问题；不增加模型可填写的原始问题参数。

`task_goal`、`completion_criteria` 和 `as_of` 保持可信服务端上下文，供项目自身查询生成、后续评审和审计使用；不作为未知字段发送给 Search API，也不宣称上游会自动执行这些约束。已有查询生成模型继续获得目标与日期；结果的发布时间用于下游判断，日期缺失不补造，日级检索操作符不构成精确时点过滤证明。

### 3.2 输出

继续使用 `WebSearchResponse` 和现有结果项结构：

- `query` 为实际提交的规范化查询。
- `answer` 固定为空字符串，作为兼容字段保留，不拼接摘要制造总答复。
- `results[].title`、`url` 来自对应上游来源。
- `results[].snippet` 优先使用非空 `summary`，其次使用短 `snippet`，并遵守现有 4,000 字符上限。
- `results[].published_at` 映射合法的上游 `date`，未知为 `null`，不使用请求时间替代发布时间。
- `coverage` 明确为 `unknown`，`basis` 为 `unknown`；不把来源数量、关键词、排序分数或请求成功映射成完成度。
- 不伪造 token 用量；上游评分、图标等字段不扩展进入本轮公共工具结果。

先验证响应顶层对象及 `results` 数组，再逐项校验、按 URL 去重并限制结果数量。有效来源保留上游排序。异常项不挤掉其后的有效项，记录跳过数量；不能因单个异常来源丢弃整个正常结果集。缺少可用标题或 HTTP/HTTPS URL 的条目不成为证据。

上游空数组映射现有 `web_search_no_results`，不可自动重试。非空数组全部无效映射 `web_search_response_invalid`，避免把协议损坏误报为没有相关资料。

摘要仍属于外部检索材料；相关性或权威性分数不构成独立事实验证，不替代专业数据接口和实体复验。

## 四、工具、配置和执行身份

### 4.1 公共依赖

将 `WebSearchClient` 协议及 `WebSearchProviderError` 提取到搜索模块中的公共文件，避免新客户端和工具依赖旧 Messages 实现。旧异常导入可保留兼容导出，但只维护同一异常类型。

`web_search` 名称、`web:search` 权限、低风险属性、审批和来源切换策略继续使用现有机制。因查询长度收紧、答复与覆盖语义变化，工具版本更新为 `2.0.0`，不以完全兼容变更处理。

### 4.2 配置

- `BS_AGENT_WEB_SEARCH_PROVIDER` 新增 `deepseek_search_api`，迁移后默认使用该值。
- 现有 `deepseek` 模式保留，明确表示旧 Messages 服务端搜索，仅供显式配置回滚；失败不自动切换。
- 新增 `BS_AGENT_WEB_SEARCH_BASE_URL`，默认 `https://api.deepseek.com`，与模型地址独立。
- 复用 `BS_AGENT_DEEPSEEK_API_KEY`、`BS_AGENT_WEB_SEARCH_ENABLED` 和搜索超时配置；直连模式不依赖模型名称。
- 工厂、注册条件和生产配置校验按所选模式检查，不再硬编码只允许旧模式。
- URL 拼接只生成一个 `/v1` 前缀；独立搜索地址的路径约定在配置说明和测试中固定。
- 更新 `.env.example` 和 README，说明切换方式、摘要语义及手动回滚方式。

启用但凭证缺失时，生产配置按现有严格校验机制明确失败；本地保留原有无凭证不注册搜索的行为，并给出不含凭证的原因。不静默使用模型地址替代独立搜索地址。

### 4.3 目录与回执

搜索仍为本地平台工具，执行绑定的 `provider` 保持 `local`，以保留现有 `run_with_context` 通道。`implementation_id` 区分实际客户端实现，非秘密配置摘要包含模式、搜索地址和影响执行的配置；模式与摘要变更进入工具目录身份。

不把凭证及其哈希放入执行绑定。配置值是绑定的非秘密身份，不意味着向模型披露连接信息。

不在迁移时批量重写历史 checkpoint 或回执。目录或绑定不匹配时继续使用现有一致性保护，不能将旧回执静默复用于新实现。显式配置旧模式是后续运行的执行路径回滚，不保证恢复正在执行的历史快照。

## 五、证据消费与恢复适配

第一阶段同时覆盖普通执行、旧权限回退和批次权限恢复三条路径，不能只验证普通 `web_search`。

1. 原始 `ToolCallResult` 按现有审计路径保存有界来源结果。
2. 普通任务内容压缩继续保留来源摘要、URL、发布时间与未知覆盖状态。
3. 批次恢复的 `_content` 增加有界 `snippet`、`published_at`，避免只保留空 `answer` 与标题链接。
4. 恢复投影优先保留来源约束、验收条件和覆盖状态；在剩余现有内容预算中保留可容纳的来源摘要，缩短或省略时显式标记截断，不扩大全局上下文预算。
5. `EvidenceProjection` 继续集中来源和去重，投影后的来源表保留摘要，不因空 `answer` 丢弃证据。
6. Planner 和合成节点获得明确语义：空 `answer` 不代表无结果，`coverage=unknown` 不代表目标已完成或确定缺失，是否满足验收条件仍须依据来源判断。

不新增搜索模型或覆盖分类模型来补回旧 `answer`。不依据未知覆盖状态强制重搜、强制 replan 或宣告任务完成；保持现有调度判断职责。

## 六、错误、超时与观测

### 6.1 错误

保留工具对外稳定的搜索错误类型，补充认证失败、余额不足和限流的可区分错误码，并同步更新 Gateway 的消息映射。所有用户可见消息来自本地固定映射，不透传响应正文、请求头或包含凭证的异常字符串。

- 401、402：不可自动重试，说明认证或余额问题。
- 400、403、404、413 等其它 4xx：不以相同请求自动重试。
- 408、429、5xx、网络故障和客户端超时：可标记可重试，但客户端首版内部不重试，由既有外层执行和恢复规则决定是否新建调用。
- JSON、顶层结构或来源结构不合法：返回响应无效，不交给下游猜测解析。
- 进程取消及时向上传播，不转成普通失败后继续发请求。

HTTP 请求超时与工具总超时一致约束；不能将配置设为 120 秒但仍由工具固定 30 秒无说明地提前中止。执行版本及目录按实际生效的超时冻结。

### 6.2 观测与预算

每次实际 Search API 请求记录一个 API span，关联既有工具观测；记录实现模式、耗时、HTTP 状态、错误分类、有效结果数、跳过数量及是否截断。查询和来源按现有内容策略有界记录，`metadata_only` 模式不额外泄露文本。

直连 Search 不记录为 LLM Generation，不上报虚构 token 用量。旧模式仍保留已有逐轮 Generation 和用量测试。

搜索调用预算与持久化回执继续走现有机制；一条获准的新工具调用最多发起一次实际 Search 请求，复用 settled 回执时不请求上游，未决调用不因只读而自动重发。观测失败不得中断业务请求。

## 七、验证与验收

### 7.1 确定性测试

1. 使用 `httpx.MockTransport` 核对请求路径、Bearer 鉴权、查询规范化、条数映射、可选原始问题和 `need_content=false`。
2. 覆盖中文 Unicode 长度、空白、128/129 字符边界；超长时没有实际 HTTP 请求，不静默截断。
3. 覆盖长摘要优先、短摘要回退、字段上限、日期、URL 去重、部分异常来源和超额结果。
4. 区分空结果、全无效来源、非法 JSON、错误顶层结构；覆盖认证、余额、限流、超时和网络错误的固定消息及重试标记。
5. 直连模式返回空 `answer` 和未知覆盖，无模型调用；可信上下文不会变成工具可伪造参数。
6. 默认配置、关闭、缺凭证、生产校验、显式旧模式和独立搜索地址行为有测试。
7. 新旧实现或配置切换改变目录与执行绑定身份，仍能通过本地工具路径接收上下文；回执复用无新增远端请求。
8. 普通任务、两类权限恢复及来源集中投影保留摘要和日期，截断后仍是合法、有明确限制的证据内容。
9. 直连观测无搜索 Generation，无 token 或密钥泄漏，内容策略生效；旧模式观测回归通过。

完成上述针对性测试后运行适当范围的后端回归和静态检查。未运行的集成环境检查必须明确记录，不能把跳过称为通过。

### 7.2 真实接口与研究链路

在实际配置可用时，以实体关系核实、当日新闻及估值资料三类问题做小批验证，比较迁移前后来源、结果摘要、真实请求次数、耗时和模型调用数。固定目标与验收口径，动态搜索结果不要求逐字一致。

必须确认不再请求搜索 Messages API、恢复路径仍可读到事实材料、缺失指标没有被相关资料替代、工具验证仍是证券身份进入专业数据工具的必要入口。

直连接口与完整研究链路分别记录结果。API 请求成功不等于研究质量通过；无凭证、网络限制或其他外部依赖不足时，明确记录对应未验证部分。性能只报告实测，不承诺固定提速比例。

## 八、第二阶段 Fetch 边界

后续新增独立 `web_fetch(url)`，使用 `POST /v1/tools/fetch` 返回的标题和 Markdown；项目补充请求 URL、抓取时间与截断信息。

接入前单独明确工具权限、抓取预算、URL 校验、正文体积、候选披露、执行回执和恢复策略。搜索到 URL 后由现有 Planner 规划依赖任务，用户直接提供 URL 时也应能发现读取能力。不把 Fetch 偷藏进本阶段 Search 客户端，不把本阶段搜索授权扩展为任意抓取。

## 九、设计自检

- 已明确用户同意的第一阶段与后续 Fetch 的边界。
- 已区分来源摘要、搜索总答复和目标覆盖，未新增隐含模型生成。
- 已明确 128 字符约束、真实原问题条件及未知日期的处理。
- 已覆盖权限恢复丢失摘要的消费问题和既有目录身份、上下文注入约束。
- 已明确显式回滚不能绕过历史快照保护，失败不自动换实现。
- 已区分离线协议验证、真实接口可用性和完整研究质量验收。
