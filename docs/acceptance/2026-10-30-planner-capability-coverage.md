# Planner 能力覆盖与补召回验收

## 实现边界

当前分支 `codex/public-mcp-documentation`。首次 Planner 优先按必要事实确认实际取证能力；可按缺口补 BM25 一轮，每轮最多三个能力短句。原有候选保留，首次最多五张卡，补召回后总计最多八张，字符与完整输入契约预算保持不变。模型声明的未知能力也可按其 task.tool_search_query 路由补召回，不复制整个目标作为检索词。

最终按实际调用返回范围合并或拆分，互补任务独立执行，同一任务内同来源仍至多一个工具。工具层保留 Planner 绑定的同源候选，同时允许其他来源备用，不再让重新排序覆盖已选能力。没有新增业务结果自验节点，没有调整合成层验收与兜底重规划。

## 验证

- 538 项相关单元与集成回归通过，耗时 18.84 秒。涵盖新增协议、非法 JSON 结构修复、单轮预算、旧引用绑定、原候选保留、卡片预留、查询市场范围、进度 JSON 缓冲重启，以及原有参数修正、权限恢复、Skill、来源队列与任务调度。
- Ruff 和 `git diff --check` 通过。
- 独立只读评审发现的逐字返回说明门控、旧候选丢失、空值类型异常和补召回卡位问题已修复；最终复核未发现新的阻断问题。

## 真实模型规划

使用原问题、当前真实 MCP 目录及已缓存说明，只调用模型生成首次计划，没有查询财务业务数据。模型先提出三条必要能力检索短句，经一轮同快照 BM25 补召回，最终形成两个互不依赖的任务：

1. 利润表：取得 2024 年收入和归母净利润，绑定 `mcp.tushare.income`。
2. 现金流量表：取得同期经营活动现金流量净额，绑定 `mcp.tushare.cashflow`。

原始响应中未知证券代码保持待核实，不从记忆补入错误标识。最终计划通过原有类型与候选引用门控。本次共三次模型调用，含一次覆盖映射的格式修复，没有消耗合成层重规划轮次。最初验收脚本在节点成功返回后，报告生成对嵌套修复请求处理不当而出现 KeyError；报告脚本已修复，机器记录依据捕获的真实响应重建，没有为生成报告再调用模型。

此前只增加补检索许可和自然语言约束的试跑仍会过度合并，不能据其宣称修复；后来优先能力确认、显式缺口路由与候选预算修正后，才取得上述结果。真实规划记录见同名 JSON。

## 限制

没有重新执行整条用户研究或验证最终财务回答。覆盖关系仍由模型判断；结构校验不能证明业务口径正确或保证所有问题都能一次规划完整。代码尚未提交、合并，历史未提交修改保留。
