## 修改结果

先核对 `_render_answer` 实际构造的输入，再修订合成提示：关联读取用户信息、任务结果、证据正文及集中来源表；阶段判断、限制提示和执行状态不能单独决定 goal 完成与否。逐项输入说明见 `2026-10-26-synthesizer-input-audit.md`。

新流程本就由合成调用同时完成判断和回答；首次调用改为开启已有 thinking 模式，旧流程保留原有显式分析交接条件。没有新增独立审核节点、目标协议、来源权限、输出字段或案例公式，原有预算、重规划和失败重试继续生效。

## 对照证据

单纯追加通用目标约束的早期尝试未通过原 trace。核对输入后，同一原始输入在关闭 thinking 时仍出现错误推导；隔离开启 thinking 的一次对照通过。随后实际生产节点的最终样本也通过。这支持本次组合修改，但单次对照不足以证明全部根因，不能归因于提示词单一因素。

最终13案包括：原始 trace、比较分析、允许的公开来源恢复、文档摘要、条件计算、辅助任务失败、必要任务遗漏、真实证据冲突、明确要求核验、前提纠正、预算耗尽，以及答案仅在 request_context 或 evidence 中的场景。

- 原 trace 正确采用来源中的约1.92亿元基数，不再生成错误基数及虚构冲突，也未把额外核验当作回答前置条件。
- 必要取证遗漏、真实冲突和明确要求核验仍申请相应补证；预算耗尽明确说明无法比较，未假装完成。
- request_context 单独提供假设数据时正确算出40%；evidence 单独提供合同时正确答出18个月。
- 原11个场景的 `user_prompt` 与 before 逐项完全相同；未通过改写事实、修改 goal 或重放原 Run 获得通过。

所有响应经过独立语义阅读。自动表达式仅作已知错误粗筛，并有三个负例防止“出现正确数字就算通过”；不能代替语义评审。除原 trace 的固定资料外，其余均为合成材料，不代表真实公司或基金数据。本次模型验证不执行 MCP、搜索或修改原业务 Run。

## 调用与成本

最终13场景共15次模型调用。条件计算首次 JSON 含未转义换行，辅助任务失败首次返回普通正文，均沿用既有一次格式修复；其他场景各1次。代码仍保留推理空响应降级，不能承诺所有请求都只有1次调用。

归档记录保存每次请求的 thinking、格式修复原因、实际正文、提供方 token 用量及每个场景总耗时。本批耗时中位数2.304秒，范围1.049至10.631秒，包含缓存和并发影响；不是受控性能基准或服务承诺。推理可能增加 token 和延时，未据此宣称相对旧配置更快或更省。
