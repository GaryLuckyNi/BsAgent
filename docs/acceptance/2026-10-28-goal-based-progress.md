# 复用目标与任务展示的验收

## 已实现行为

- Planner 首次、修订、重命名任务均不再要求或保存 `public_summary`；输出 schema 只保留必要任务字段。
- 入口完成后展示已有 `goal`，规划完成后本地列出 `tasks[].task_goal`；任务执行展示既有目标与真实状态，不把“规划完成”当作任务已完成。
- Analysis、Skill 不再把结果正文截取为“研究发现”。实际分析内容、固定 Skill、执行结果与最终合成保持原职责。
- 删除专用摘要提示、结果摘要提取与其文本清洗。保留任务目标的公开文本清洗、工具进度、来源确认和真实失败状态。
- 数据推演仍要求明确待求量、公式、必要自变量及核对值，将关系放入任务目标和完成条件，不新增只为思考公式的任务。

## 兼容性

旧检查点允许携带 `public_summary`，读取时只忽略这一旧字段，其他未知字段仍严格报错。序列化及模型输入不再携带摘要；原始持久计划不被归一化改写，计划签名与待恢复申请绑定不变。

前端保留历史 `summary` 事件读取，新执行使用 `goal`、`plan`、`activity`。公开计划最多 12 项，每项沿用目标清洗，保存上限 3000 字，刷新后不因旧 500 字上限丢失后半计划。

用户输入中断等待选择时保存公开进度；用户输入恢复完成时沿用该消息的进度元数据，查询限定租户与运行，不改变执行状态、授权或工具副作用处理。已补中断前与恢复完成后的数据库读取测试。

## 性能边界与离线样本

原 trace `e63644e40326c60cd3b2c2ab910d5ad8` 的规划包含 96 字摘要。只删除摘要字段后，紧凑 JSON 从 1808 字符变为 1692 字符，减少 116 字符；3 个任务的执行契约完全相同，旧原始输入保持不变。

脚本 `docs/acceptance/goal_based_progress_probe.py` 还验证了现有目标和任务能直接产生 goal/plan 展示事件。记录保存在 `docs/acceptance/2026-10-28-goal-based-progress.json`。该结果是离线字段删除比较，字符数不是 token 数，也不是实际模型重新生成的结果；没有测量端到端耗时。

Planner 摘要原本与计划在同一次模型调用中生成，Analysis/Skill 的展示摘要原本也只是本地截取。本次减少专门的输出字段及展示逻辑，不声称减少业务模型调用次数，也没有删掉必要分析。

## 验证

- 先记录失败：原实现对应 11 项后端失败、2 项前端失败；随后补充的旧摘要输入与中断恢复 3 条路径也先确认失败，再修复。
- 最终相关后端测试 195 通过，目标/计划流式保存与恢复集成测试 5 通过。
- 最终后端全量回归：2145 通过、53 跳过、2 个既有警告，耗时 198.48 秒。
- 前端全量 92 通过，生产构建通过。
- 独立审查指出的旧摘要模型输入与中断恢复保存边界已修复并复核。
- 修改的图节点、规划、事件代码、单元测试及离线探针 Ruff 通过。API 文件有既有 26 项 FastAPI B008，数量与 HEAD 一致，排除该规则后通过；集成测试文件的 4 处既有 lint 问题也与 HEAD 一致，不借本次改动重写无关代码。
- 全量回归曾发现合成输入投影补出了原本未设置的默认字段，现已使用 exclude_unset 保留原计划形状，来源边界回归通过；未放宽原有一致性断言。
