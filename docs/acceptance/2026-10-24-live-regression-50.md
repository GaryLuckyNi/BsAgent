# 50 条真实回归与 Langfuse 链路审阅报告

状态：待用户确认；本轮仅测试、取证和分析，未修改业务代码或配置，未修复或清理数据库回执。

## 一、结论

这批测试说明：当前问题不只是模型单次响应慢。更优先的问题是权限错误没有进入恢复机制、重新规划绕过来源切换确认、部分已取得的结果没有进入最终回答，以及工具适配和数值计算不可靠。

与此同时，“不需要外部能力的问题减少模型调用”确有优化空间：5 条纯概念问题每条都有 **6 次前台 generation**，平均根耗时 **32.91 秒**。但不能简单取消所有 Planner：混合问题、带来源限制的问题和多任务研究仍需规划，重点应是分流、缩小规划契约和保留证据。

本次不是“50 条全部通过”：

| 项目 | 实测结果 |
|---|---:|
| 真实用户问题 / 独立测试会话 / 独立 run | 50 / 50 / 50 |
| 已关联并审阅的真实 Langfuse trace | 50 |
| HTTP 200、协议 completed、后台 producer_done | 各 50 |
| `research_answer` / `execution_error_response` / `out_of_scope` | 35 / 14 / 1 |
| 观测记录 / generation 记录 | 1,981 / 373 |
| 前台 generation / 后台质量评估 generation | 324 / 49 |
| 工具持久回执：settled / unknown | 46 / 15 |
| 实际用户确认 interrupt | 0 |
| 根耗时：中位数 / P90 / P95 / 最大值 | 16.962 / 44.437 / 74.910 / 114.289 秒 |

`research_answer` 只是响应类型，不等于目标完成、数字正确或来源充分。不得把 35/50 当作业务通过率。

### F01：权限分类没有覆盖真实 TuShare 错误格式

本批底层 Langfuse 明确记录 **13 次“没有接口访问权限”**，涉及 `rt_idx_k`、`anns_d`、`income_vip`、`limit_list_ths`、`fina_indicator_vip`、`us_fina_indicator`。上层却返回：

```text
status=failed
execution_state=uncertain
error.code=mcp_tool_execution_failed
error.details.failure_stage=remote_tool_error
```

例如 014 的底层错误为 `tushare API 错误 [40203]: 抱歉，您没有接口(rt_idx_k)访问权限…`，上层丢掉了权限语义，回执变为 unknown；再次调用在本地被 `tool_side_effects_unresolved` 拦截，最终只有“存在尚未核实的工具执行”，没有 interrupt。

对保存的真实错误做了**离线分类回放**，不重新请求 MCP：13 条权限错误及 1 条限流错误全部返回 `classification=None`。当前 `mcp_permission.py` 的文本规则使用行首匹配，不能覆盖真实文本前缀及带接口名的拒绝句式；`mcp_http.py` 随后归一为通用远端错误。这是已确认的匹配缺口，而不是只凭最终文案推测权限问题。

但 **40203 不能直接写死为权限拒绝**：036 的相同错误码实际表示“频率超限（1次/分钟）”。应在 MCP 适配边界按失败信封、代码与消息主体分类，分别保留权限、限流、参数错误、超时等语义，不维护“哪些接口只读/无权限”的逐接口白名单。

分类与“能否证明未执行”仍需分开。不能为了消除 unknown，把所有异常、超时或部分执行结果直接 settle；来源恢复还需核对服务端的拒绝阶段契约、冻结策略和实际候选。

### F02：确认机制可以被重新规划绕过

021：`anns_d` 权限失败 → Planner 创建公开信息新任务 → `web_search` 普通搜索成功。全程没有确认中断，checkpoint `recovery_items/batches/outcomes` 均为空。

045 更明确：用户在原问题中写了“**切换来源需确认**”，Router 也保留该约束，但 `anns_d` 失败后仍重新规划并直接搜索。该问题不能用“用户本来允许公开补充”解释。

建议把来源切换约束绑定到研究目标/证据需求及恢复来源，而不是只依赖原 call ID 或某个 recovery 分支。Planner 改任务 ID、改描述不应获得新的切换授权。保持用户此前确认的原则：同批拒绝可合并确认，但仅覆盖弹窗列出的任务。

### F03：已有成果没有可靠地进入最终回答

存在两条不同路径：

1. **失败整体盖过成功部分。** 031、032、034 的 `analysis_agent` 已生成理论解释或假设 PE=20 的结果，但工具权限失败后最终只输出两行执行错误。042 已取得主营业务数据，也没有作为部分成果展示。
2. **计划修订造成证据遗失。** 045 的原始 MCP 结果确实包含贵州茅台归母净利润及宁德时代行情。修订后 Synthesizer 的实际 generation 输入只剩比亚迪搜索材料，`research_assessment.reason` 只说前两项“已核实”，没有数字。最终模型只能回答“已核实但材料未列具体数值”。这不是合成模型忘记读数据，而是数据没有传到它的输入。

应保留跨修订的证据集合，按用户原始需求引用相关历史结果。允许“部分完成＋明确缺口”，同时继续禁止用 Planner 的状态摘要充当事实证据。无需为此新增一层通用评判 Agent。

### F04：数字与单位错误不能靠模型自称“自洽”兜底

- 012：TuShare `amount=22440211.716`，正确换算约 **224.402 亿元**，回答写成约 **2244 亿元**；还将含 +2.024% 的前四日称为涨跌均在 ±2% 内。
- 013：`amount=451328.26` 的单位是千元，回答却写成 **451,328.26 元／45.13 万元**，差 1000 倍。
- 020：5 行 `bz_sales` 的算术和为 **179,667,509.14 元**，回答为 **189,667,509.14 元**；利润合计相应从正确的 **84,880,261.48** 写为 **94,880,261.48**。分类是否重叠是另一项限制，不能解释算术差错。
- 011、013 分别将 `1482.20 > 1480.00`、`17.80 > 17.78` 称为“低开”。这些是用户只问查询数值时额外生成的错误解读。

单位依据已核对 [TuShare daily 官方输出字段](https://tushare.pro/document/2?doc_id=27)：`amount` 为千元、`vol` 为手。

009 还暴露题目欠定处理：给定“价格上限20元”只能计算按该价格成交对应500万股，不能据此推出最大股数；更低成交价会买到更多。系统应澄清这个前提，而非顺着“理论最大”作答。

建议将金额单位、简单合计、涨跌方向等确定性计算交给已有结构化处理或轻量校验。只问数值时不要默认扩写盘面推断。002 的净现比解释也存在前后逻辑矛盾，应作为回答质量样本保留。

### F05：减少调用前，先避免“选错工具再补救”

- 014：历史指数查询选择实时指数 `rt_idx_k`，参数根本没有历史区间。
- 026、027、035：A 股指数选择 `index_global`，空结果后继续在错误能力上取证。
- 036：A 股茅台选择 `hk_daily`，空结果后重复相同错误市场查询，进一步触发限流。
- 047：A 股宁德时代财报选择 `us_fina_indicator`。
- 043：三个公司收入被压成一个单工具任务，执行只覆盖茅台，其余主体没有取得数据。
- 044：三个指数被压成一个任务，但只查询上证 `index_dailybasic`，日期参数为 `2025-09-01` 而非接口要求的 YYYYMMDD，且未取得目标收盘点位。

这里不是“拆得越少越好”。在单次 Tool Agent 只能执行一个工具调用的约束下，计划必须与单工具能力对齐：能批量且覆盖目标就批量；不能就拆成必要的独立子任务。候选应表达市场、主体、历史/实时、输入范围、输出指标；执行前做能力契约检查，不靠写死接口名单推断权限。

### F06：调用链冗余及反馈修复

001 的实际前台链路为：

```text
Router 1次 → Planner计划1次 → Tool Agent直接写概念答案1次
→ Planner反馈1次 → 修复无效synthesis_task_id再调1次 → Synthesizer重写1次
```

前台共6次；另有后台 judge 1次。002—005、007—010 也各有6次前台生成。纯概念5条平均根耗时32.91秒，而非用户所需的一次短回答成本。

全批可见 **18 次带 `repair` 的 Planner generation**，其中多条只是已经执行完任务后仍指定 `synthesis_task_id`，再用一次模型调用改成 null。保留验证是必要的，但应缩小模型契约、明确合法选项，能在不改变意图前提下确定性规范化的就不再调用模型修复。

建议保留 Router；纯解释/仅材料内分析走 Router → Synthesizer；真实混合问题、外部取证、Skill 或依赖编排进入 Planner。Planner 不直接输出给用户的自然语言答案。此为建议，**尚未改动路由**，也未通过对照实验量化优化收益。

026 包含一次约61秒的 generation 离群值；遵从用户此前要求，本报告仅记录耗时，不追查等待原因，不据此推断普遍性能退化。

### F07：空结果、已执行和目标满足被混在一起

039 的 `express` 返回空；Planner 想另建任务补原始营收，被验证器判断“与已成功任务取证目标重复”，两次反馈后 `planner_feedback_invalid`。044 同样因空结果被当作“成功历史”，合理补证被阻止。017 则是修改已完成任务仍复用原 ID，反馈修复失败后停止。

应分别表示 transport/execution、数据是否为空、验收条件覆盖、还允许什么补证。去重应防止同参数、同来源的无意义重放，不应禁止对未覆盖目标选择适配的另一接口；也不能简单放开所有重复任务。

### F08：Skill 的实际可用性与启用配置不一致

管理接口有4个启用 Skill，但启用业务意图只有 `financial_research.general` 和 `financial_research.cross_asset`。`company_snapshot`、`financial_report_analysis`、`risk_scan` 的支持意图为 `task_workflow`，且定义依赖 `mcp.local.stock.*`。

046—048 明确点名这些流程，实际没有创建相应 `skill_workflows`，而是退成普通 tool 计划。因此不能直接断言是 Router 代码错误，配置/依赖不匹配本身已有证据。系统应明确提示“流程当前不可执行/依赖不可用”，不应让用户以为执行了指定流程。

049 确实进入 `yzj_reasearch`；第一步 `stock_basic` 超时后停止，未继续虚构管理层数据。此次未覆盖该 Skill 的成功输出或中断恢复，应保留覆盖缺口。

### F09：Router 范围判断需要边界样本

006 只要求用用户给的营收和利润算同比及净利率，被高置信度判为范围外；007、008 同类材料内计算却能进入投研流程。建议补充“无公司代码、假设财务材料”的范围样本，不要为了省 Planner 把它们拒绝掉。

### F10：重复输入要按实际 generation 判断

001 两次 Planner 反馈的真实 generation 输入，1921字符的同一段模型答案同时出现在：

```text
observations[0].content
planning_constraints.user_materials[0].text
```

这既重复耗 token，又把模型自产内容标为用户材料。应保留来源角色并单点引用。

但本批对所有前台 generation 的解码检查中，没有确认合成层存在同等规模的“外层 query/answer ＋ artifact query/answer”重复。Synthesizer 已使用 `research_materials` 和 `source_ids/sources`。审计 state 与实际模型 prompt 的重复不是一回事，不能把可追溯字段一概删掉。

### F11：搜索证据与预设答案污染

019 用户未给出净息差2.00%，Tool Agent 却把2.00%加入搜索 query；搜索返回后，最终回答又专门“纠正”这个用户没有提出的值。这是内部假设污染需求，已从输入输出确认。

多个真实搜索结果只有 title/url，`snippet` 为空、`published_at` 为 null。027、045 的 `answer` 还包含未被稳定解包的 JSON 字符串。下游能写出流畅报告，不代表独立核实了对应网页正文。

024 以未覆盖官方整月公告的材料给出“整月不存在降准”的强否定，是证据充分性风险；本报告**没有据此断言该金融事实本身错误**。建议保留实际摘录、时间、检索范围与 coverage，把“搜索模型总结”与“可独立审计的原文证据”区分开，不新增一个同样只读摘要的 LLM 来循环自证。

### F12：观测与业务成功不能混为一谈

- 14 条 `execution_error_response` 的 run 仍为 completed：协议收尾没有失败，但业务目标未完成。监控应另有业务结果/覆盖状态，而不是把 completed 改成传输失败。
- 最终刷新后，027、045 共5个 generation 仍缺 input 或 output；具体 observation ID 在 verification.json。50条trace均存在，不能把局部IO缺失说成trace丢失。
- 373个generation的 `costDetails` 都为空。已记录的 `usageDetails.total` 合计847,160，前台775,432，包含提供方缓存等口径，**不是实付账单**；不能用未配置的单价估算精确费用。
- 观察到49条后台judge，不保证每个run都能取得judge证据；尤其不能以自动高分替代本报告中的数值和链路核验。
- 耗时取根span；没有把并行子span简单相加。普通tool包装和内部同名TOOL span也没有按两次远端执行计数。

## 四、已验证的正向路径

- 041 三个同批独立 `daily` 任务均实际发出，产生3条settled回执；两项本地等待后继续，没有终态误失败。说明上一轮“三任务健康路径”修复在本批真实环境有效，不能笼统说完全没修好。
- 015 区分000001.SZ股票和000001.SH指数正确；025正确使用交易日历识别周末；037保留TuShare-only，没有擅自网页替代。
- 033 没有把空公告搜索当作“确定没有公告”；多个研究回答保留缺口、数据时点和非确定性结论。
- 独立测试会话隔离生效：014等会话产生unknown后，其他新测试会话仍可正常取得行情。当前执行门禁按tenant＋session_key检查；不代表在这些测试会话继续对话不会被阻塞。

## 五、建议顺序（等待确认，不实施）

1. **先修正确性和用户控制**：真实MCP失败分类与可信执行阶段 → 来源切换约束不可被重规划绕过 → 成功部分/跨修订证据不丢失。保留真正不确定执行的门禁。
