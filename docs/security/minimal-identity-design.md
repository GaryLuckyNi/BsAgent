# 复用现有 OIDC/JWT 的最小授权接入设计

日期：2026-11-02。状态：分批实施中；保留最初方案对比，未覆盖部分仍为设计草案。

后续用户已要求继续第 1 批，按下文方案 B 实现应用权限目录及普通请求/工具审批恢复接入，见 [实现与启用说明](current-permission-directory.md)。第 2 批进一步实现任务 worker、工具派发、用户选择和审批恢复的当前权限与初始上限，见 [验收记录](reports/2026-11-02-run-authorization-implementation.md)。第 3 批也已实现 [Admin 用户与服务准入](admin-authorization.md)。其余批次仍为设计范围；下文保留最初方案对比，不能据此认为 Admin/RAG 和全链路恢复已经完成。

## 1. 已确认基础与目标

- 用户明确主应用已有 OIDC/JWT；复用现有前后端认证接口，不重建登录体系，不新增第二套账号密码服务。
- 当前源码默认本地 mock，不代表实际运行实例一定使用 mock。实际 issuer、audience、回调及可用身份服务应在接入验收时核实，本文不记录凭证。
- 安全能力通过公共框架和设施适配层接入，Agent/业务节点不直接依赖安全模块。
- 本期围绕当前能力，包括真实身份下的审批、后台执行和恢复；未来代码执行、交易等边界继续保留在 [TODO](TODO.md)。

目标是形成“可信身份 → 当前授权 → 资源约束 → 执行 → 审计”的闭环，而非仅让浏览器出现登录按钮。

## 2. 复用与补齐范围

| 部分 | 直接复用 | 必须补齐 |
| --- | --- | --- |
| 主应用登录 | [OIDC 控制器](../../frontend/src/auth.ts)、登录入口和回调 | 登录失败/过期不降级为固定用户；受保护环境的运行配置校验 |
| JWT 验证 | [JWT provider](../../backend/app/security/jwt_provider.py)、[认证依赖](../../backend/app/security/dependencies.py) | 受信身份映射、token 用途与服务主体区分；授权由可信权限源组装 |
| 业务权限 | 现有 require_permission、会话/资产归属检查 | 可解析当前权限的真实 provider，替换固定 MockRbacProvider；配置与实际 provider 一致 |
| 审批与副作用 | 原调用 ID、参数指纹、恢复及执行回执 | 当前请求者与审批者重新授权；后台不把旧权限快照当长期通行证 |
| Admin | 现有配置接口、脱敏和内部连接读取 | 同一身份体系下的管理权限、服务专用读取权限、前端凭证及未登录处理 |
| RAG | 已有检索接口与部署分区 | 服务认证、可信请求主体绑定、文档访问范围和检索前约束 |

## 3. 当前权限源的三种方案

| 方案 | 行为 | 优点 | 主要代价 |
| --- | --- | --- | --- |
| A：仅依赖当前 JWT scopes | 每次验证 token 后直接使用其权限 | 改动最少，复用现有普通请求路径 | 旧 token 的权限可能过期；后台不能凭 user_id 获取最新授权，单独采用它无法满足本期恢复撤权目标 |
| B：OIDC 认证 + 应用权限目录 | OIDC 确认身份；受控权限目录提供当前账号状态、成员关系和业务角色 | 普通请求、审批与后台可使用统一授权源；不依赖特定身份产品的管理 API | 需要小规模权限数据及受控授予/撤销工具 |
| C：OIDC 认证 + 现有企业权限源适配器 | 接口查询已有 IAM/成员目录的当前权限 | 已有权威目录时无需重复维护角色 | 依赖实际服务能力、准入协议、可用性和撤权时效，当前尚未证实已经具备 |

**建议默认采用 B；如现有身份系统已经提供可靠的当前权限查询，则采用 C 替换同一接口。** B/C 的具体选择尚未确认，不能把 OIDC/JWT 已存在直接等同于已有当前权限目录。A 可作为认证链路联调步骤，不能单独作为完整授权验收终点。

第一版先实现一个真实权限源，不同时建设多套生产后端，也不新增通用独立权限微服务。权限目录不保存密码、refresh token 或用户登录会话。

## 4. 最小身份与角色模型

- 外部身份由受信 `(issuer, sub)` 唯一绑定，不能用邮箱、显示名或可自改资料自动合并账号。服务主体与用户主体分开标识。
- 租户成员关系和角色来自权威权限源。前端传来的 tenant_id 是请求选择条件，必须与成员关系相符；模型输出和外部证据不能选择主体。
- 首期建议单租户多用户正常使用，同时用第二个合成租户验收拒绝行为；跨租户切换和邀请界面单独规划，不默认开放。
- 现有 `tenant_1/user_1` 的开发数据不能自动归属到第一个真实登录用户；迁移必须显式绑定且保留记录。

| 主体/角色 | 允许能力 | 不自动获得的能力 |
| --- | --- | --- |
| analyst | 发起研究、访问自己有权使用的会话/资产/知识库 | 配置管理、审批、其他用户资源 |
| approver | 在 analyst 基础上，读取和决定明确授权范围内的审批 | 全局配置管理、无关会话正文；不能扩大被审批人的权限 |
| config_admin | 全局 Intent、Skill、数据源配置的受控读写 | 用户会话、私有知识库、用户工具审批或通配 `*` |
| agent_runtime 服务 | 读取运行所需的 Intent/Skill 与内部连接配置 | 修改配置、浏览器登录、任意用户资料 |
| turn_worker 服务 | 领取特定运行、提交回执、按当前用户授权执行 | 凭任务载荷中的旧 scopes 自行扩大权限 |
| rag_retriever 服务 | 请求绑定租户及被委派用户允许的检索 | 任意租户切换、上传/删除/重建索引 |

Admin 当前配置为全局范围，config_admin 因此是平台配置角色，不能伪装成已实现租户级配置隔离。角色可由受控管理员同时授予，但必须逐项显式授权。

## 5. 公共接入契约

建议增加独立公共身份与授权层，逻辑接口为：

```text
authenticate(token, expected_audience, expected_subject_kind)
    -> AuthenticatedSubject
resolve_current_permissions(subject_ref, tenant_ref)
    -> CurrentPermissionSnapshot
authorize(subject, operation, resource, current_permissions, execution_ceiling)
    -> Allow / Deny / Unavailable
```

这是拟定契约，不是已经存在的 Python API。快照包含有效状态、明确权限及 revision；签名认证失败与权限不足、权限源不可用分别处理。原有 Principal 可由适配层组装，业务节点不直接读取权限表或 OIDC 客户端。

OIDC 的 `openid/profile` 是协议范围，不能直接当成业务权限，也不能机械地与业务权限取交集导致全部拒绝。若 token 声明业务权限上限，应由固定协议解释并与当前权限源取交集，不能把任意 claims 中的 `*` 合并为授权。

受保护环境中，mock provider 只能显式用于测试，配置为真实 provider 但实际返回 mock 时启动失败。首次登录成功但没有角色/成员记录的主体不能自动成为 analyst 或 admin。

## 6. 主应用、Admin 与服务间边界

### 主应用

现有登录完成后，后端验证访问 token，再解析当前成员与权限。建议提供最小的当前用户能力查询，让前端从服务端取得显示身份和可用功能；UI 禁用只影响体验，资源授权始终在服务端执行。

登录失效时终止新的受保护请求；重新登录后的缓存与活动会话选择不能沿用另一主体的数据。保持实际资源的归属校验，包括 SSE 重放、停止、搜索、图片、Trace 和审批，不因角色统一而取消资源约束。

### Admin

浏览器登录复用同一身份提供方，Admin 前端单独作为 OIDC 公共客户端；使用专用 API audience 或等价的明确 token 用途限制，拒绝无效或用途不符的 token。现有主应用 token 是否可被 Admin 接受必须由显式策略决定，不能默认任何同 issuer token 都有效。

公开命名的配置详情仍要求配置读取权限且继续脱敏。配置写入要求 config_admin 对应操作权限；内部完整连接要求服务身份及专用读取能力。Intent、Skill 的运行时读取也应保留服务只读路径，不能加上管理员校验后把 Agent 正常加载配置一并阻断。

### RAG

后续用户已明确为外部内置 rag_search HTTP 工具；当前实际实现范围见 [调用方边界](rag-caller-boundary.md)。以下为下游协议的设计要求，不表示已经对外部服务或相邻源码实施，必须先确认实际服务支持的契约。

RAG 不新增独立登录页面。调用方必须提供可验证的服务身份，固定服务主体与用途；首选复用现有身份提供方的服务认证能力，其支持情况必须核实，未支持时另行确定受管服务凭证协议。

服务身份只证明谁在调用，不自动授权读取全部文档。RAG 还必须绑定固定部署租户，或验证调用主体被允许委派的租户/用户上下文；普通 Header 及用户 filters 不能建立这种信任。共享服务处理不同用户时，文档 ACL 在检索前强制施加；用户过滤条件只能进一步收窄。

当前按 RAG_TENANT_ID 固定分区的部署可以保留，但必须拒绝其他租户，并说明同租户用户的文档可见范围。尚无法执行 ACL 的私有文档不能按“所有人共享”降级处理。检索、上传、删除和索引维护分别授权，浏览器直连入口不能遗漏。

## 7. 后台、审批恢复与撤权

[dispatcher](../../backend/app/conversations/dispatcher.py)当前从持久化 payload 重建 Principal；这保存了请求身份，但不能证明其权限仍然有效。

目标行为如下：

1. Run 保存服务端确认的主体引用、租户、原始执行授权上限、策略 revision 和审计关联，不保存用户 bearer/refresh token。
2. Worker 领取任务、审批恢复和后续受保护调用前，通过真实 provider 获取当前状态与权限；新调用范围受当前权限和原执行上限共同约束。
3. 审批人的管理能力不能代替原请求者权限。调用 ID、参数和绑定变化仍按原有审批契约拒绝或重新审批。
4. 当前权限源不可用时，停止新的受保护派发；允许用受限系统身份保存已返回结果、执行回执和取消状态，避免丢失已发生副作用。
5. 对用户的业务停用/撤权，以权限目录提交后下一次强制检查为生效边界。检查与外部派发之间的竞态及已在途请求不能被描述为瞬时撤回或自动回滚。
6. 普通浏览器退出不自动取消已经明确授权的后台任务；需要停止任务时使用现有停止流程。身份提供方禁用、token 撤销和应用业务停用的同步时效应分别验收。

第一版建议对新派发直接查询当前权限，不启用长寿命授权缓存。后续引入缓存时必须单独定义失效与撤销时效，不能沿用历史 checkpoint scopes。

记忆后台同步同样区分“已提交候选的幂等投影”和“新增用户写入授权”；前者使用只允许处理已提交来源及对应命名空间的系统能力，后者必须获取当前权限。

## 8. 建议拆分与验收

| 批次 | 独立交付 | 关键验收 |
| --- | --- | --- |
| 1 | 当前权限源与公共适配契约，修复 provider 配置和实际行为不一致 | 无角色不默认授权；禁用/撤权生效；真实配置不能返回 mock |
| 2 | 主应用登录闭环及前台/后台统一授权 | 未登录、过期、A 冒充 B 被拒；合法研究、停止和恢复成功 |
| 3 | Admin 用户和运行时服务授权 | 匿名/无效身份不能读完整连接或修改配置；授权服务能正常加载三类配置 |
| 4 | RAG 服务协议及资源授权联调 | 固定租户冲突拒绝；上游身份可信；filters 不能扩大 ACL；合法检索成功 |
| 5 | Harness 运行期安全接入与红队复验 | 覆盖主入口、工具、模型、Store、后台、恢复及出口，失败与正常对照都有证据 |

每批必须保持正常路径。第一批之前先建立能失败的安全断言；历史探针保留为事实记录，不能只改变探针期望把原 FAIL 改成 PASS。RAG 属于同级独立工程，先完成双方协议与测试夹具，再按该工程协作约定实施，不在本仓库单方面假定协议已接通。

涉及新功能和架构实施时，从 dev 建立 feature 分支；按项目约定不创建新 worktree。本文仅文档讨论，不提前切换分支或修改业务代码。
