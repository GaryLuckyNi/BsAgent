# 身份认证现状、成因与后续顺序

日期：2026-11-02。状态：基于源码和本地验证的分析，建设顺序为建议；第 1、2 批已完成本地实现与相关回归。

本文保留第 1 批实施前的诊断记录。后续已按应用权限目录推进真实 provider、普通请求及工具审批恢复接入，第 2 批也已覆盖 Agent turn worker、工具派发和用户选择恢复的当前权限与初始上限；当前实现与限制见 [权限目录说明](current-permission-directory.md)；下文对 MockRbacProvider 工厂的描述对应改造前事实。

## 1. 当前状态

不能用“没有注册/登录页面”直接判断后端是否有认证；注册、认证、权限判断、资源隔离和服务间信任是不同环节。

## 2. 成因与此前红队结果的解释

从实现和历史设计可推断：主应用先按外部 OIDC/JWT 接入设计，日常开发使用 mock；Admin 与 RAG 先作为受信服务搭建，各自采用内网信任或部署固定数据分区。三条路径尚未汇合成统一身份、角色、服务主体与授权契约。

本地没有登录体验的直接原因是 OIDC 配置缺省时禁用，而不是主应用完全没有登录代码。注册也可以由外部身份服务承担，不要求每个业务系统实现账号密码接口。

本地补充验证：在 test 环境将 `BS_AGENT_RBAC_BACKEND` 设为 `principal`，`get_rbac_provider()` 实际仍返回 `MockRbacProvider`。这说明仅打开 JWT 或满足生产配置校验，无法保证恢复及后台权限刷新使用真实权限源。

因此，[首轮红队报告](reports/2026-11-02-red-team-report.md)中的两项本地 FAIL 继续有效，但应按“尚未建设/接通的身份边界”理解，不能描述成“已有完整登录与授权系统被突破”。RAG 不传 tenant/user 并非必然错误：若部署严格按租户独享，必须证明服务到固定租户的可信绑定；若多个用户拥有不同文档权限，还必须补齐用户/组授权。

## 3. 建议的建设顺序

### 第一步：确定最小身份模型并约束开发环境

- 明确单租户内多用户的首期范围；如果确有多租户需求，再同时验收租户成员关系与隔离，不能由客户端自由选租户。
- 定义用户、租户成员关系、分析师、审批者、管理员和服务主体；权限由受控配置或可信权限存储授予，前端及模型不能指定角色。
- 账号先采用管理员预建或邀请加入；公开自助注册作为独立产品需求，不作为接通认证的前置条件。
- 本地 mock 仅用于明确的开发环境。当前开发脚本默认监听 `0.0.0.0`；建议优先收敛到回环地址，需要局域网访问时显式配置边界。未核实实际运行监听与网络暴露，本文不声称已产生公网风险。

完成标准：两名普通用户、一名审批者、一名管理员的权限矩阵明确，开发与受控部署不能混淆。

### 第二步：接通统一身份服务与主应用

- 复用已有 OIDC/JWT 路径，接入一个统一身份服务；有企业 SSO 则优先复用。身份服务承担登录、账号创建/邀请、密码或其他认证方式及会话生命周期。
- 先打通主应用登录、回调、退出和过期处理，API 在受保护环境只接受可信 token；失败时不静默降级成固定用户。
- 替换固定 mock 权限解析，让普通请求、审批恢复及后台权限刷新使用一致的授权源；明确禁用账号、撤权和已有 token 的生效时效。

完成标准：未登录不能读取业务数据，A 无法冒充 B；合法用户可以正常研究，审批恢复不因 mock 角色映射扩大权限。

### 第三步：接入 Admin 与 RAG 的用户/服务授权

- Admin 浏览器使用同一身份体系，单独授予配置读写权限；普通主应用用户不能自动获得管理权。
- 主应用和 worker 读取内部配置使用服务身份，完整连接仅允许受控服务获取；用户 token 与服务凭证职责分开，不能把任意用户 token 透传给任意下游。
- RAG 可保持内部 API，不必先建设独立登录页面；检索入口验证受信服务身份，并绑定固定租户或经验证的委派用户/租户上下文。
- 用户可见文档范围由可信权限计算，强制作用于检索前的过滤和相关索引入口；用户 filters 只能收窄范围。浏览器若仍能直连 RAG 管理/上传接口，该入口也要有身份与权限。

完成标准：匿名及普通用户不能读完整 MCP 连接或改配置；伪造身份/filters 不能扩大文档可见范围，合法服务和用户路径正常。

### 第四步：在可信身份之上接入 Harness 安全模块

- 安全模块消费可信 Principal、资源权限和调用来源，继续承担工具限制、审批、出口控制、记忆污染约束、预算与审计；不自行复制账号系统。
- 公共适配层负责接入，Agent/业务节点保持不直接依赖安全模块；已有模型检测可以继续研究，不能冒充真实身份授权验收。
- 先重跑 RT-13～RT-20、RT-25、RT-31 的身份和硬边界，再补真实模型注入评估。保留合法任务对照，不能用全部拒绝获得“安全通过”。

完成标准：身份、资源、工具和恢复链路的确定性测试通过，才据此判断运行期 Agent 防护的实际覆盖。
